Повторення Streamable HTTP

Навіщо повторюємо

Досі qauto MCP server працював через stdio: Cursor запускав процес і передавав credentials у env.

Перед міграцією освіжимо, що таке Streamable HTTP і чим він відрізняється від локального subprocess.

Повторення Streamable HTTP

Що це і навіщо

Transport layer визначає, як JSON-RPC доходить між Host і Server. Формат повідомлень той самий — змінюється лише доставка.

Streamable HTTP — мережевий transport: сервер як окремий процес з HTTP endpoint. Один процес — багато клієнтів. У stdio кожне зʼєднання — окремий subprocess.

Повторення Streamable HTTP

Обмеження

1. Host сам стартує процес

Cursor/Claude запускають uv run python -m qauto_mcp і тримають stdin/stdout. Немає окремого сервера: закрив IDE — MCP помер. Не підключиш другий клієнт до того самого процесу.

2. Одне з'єднання = один subprocess

Кожен Host піднімає свій процес. Inspector, Cursor і Claude Desktop — три копії сервера, три сесії, три логіни в QAuto.

3. stdout зайнятий протоколом

У stdin/stdout ходить JSON-RPC. Туди не можна писати логи — зламаєш протокол. Діагностика лише в stderr, і то обережно.

4. Секрети тільки через env процесу

Працює, бо Host інжектить QAUTO_EMAIL / QAUTO_PASSWORD при spawn. Для HTTP Host процес не запускає, тому той самий блок env у mcp.json уже нічого не дає.

5. Немає нормального remote

stdio — локальна труба. Не вийде покласти MCP на сервер/Docker і підключитись по URL. Для цього якраз Streamable HTTP.

Повторення Streamable HTTP

Як це працює

Раніше в MCP був окремий transport HTTP+SSE з двома endpoint'ами. Streamable HTTP замінив його: тепер один endpoint, наприклад /mcp, і через нього йде все.

Клієнт
Сервер (/mcp)
1. POST /mcp — initialize
200 + Mcp-Session-Id: abc
2. POST /mcp — notifications/initialized
202 Accepted
3. GET /mcp (SSE) — опціонально
відкритий потік — сервер пише сам
4. POST /mcp — tools/call
JSON або SSE-потік з відповіддю
5. DELETE /mcp — завершення сесії
Клієнт
Сервер (/mcp)

«Streamable» означає, що будь-яка відповідь може стати потоком, якщо сервер вирішить, що так краще: простий виклик — POST → JSON, довга задача — POST → SSE. GET потрібен лише для повідомлень, які сервер ініціює сам.

Повторення Streamable HTTP

stdio: command + env

Host сам стартує процес і інжектить credentials у env:

{
  "mcpServers": {
    "qauto-course": {
      "command": "uv",
      "args": ["run", "main.py"],
      "env": {
        "QAUTO_EMAIL": "user@example.com",
        "QAUTO_PASSWORD": "YourPass1"
      }
    }
  }
}

Повторення Streamable HTTP

HTTP: url + headers

Host не запускає subprocess — ті самі ключі йдуть у headers:

{
  "mcpServers": {
    "qauto-course": {
      "url": "http://127.0.0.1:8000/mcp",
      "headers": {
        "QAUTO_EMAIL": "user@example.com",
        "QAUTO_PASSWORD": "YourPass1"
      }
    }
  }
}

Повторення Streamable HTTP

stdio vs Streamable HTTP

  • Desktop / локально без окремого процесу → stdio
  • Окремий процес, Inspector, кілька клієнтів → Streamable HTTP
  • Production remote → Streamable HTTP + auth

Блок 2

Логування

Два рівні: transport (FastMCP) і додаток (tools + httpx)

Логування

Два рівні логування

Після міграції на Streamable HTTP зручніше дивитися, що відбувається на сервері. Логування — не одне ціле: є рівень MCP / transport (framework) і рівень додатку (виклики QAuto API у tools).

На stdio stdout зайнятий протоколом MCP — туди не можна писати діагностику. Після переходу на Streamable HTTP transport не займає stdout: у конструкторі FastMCP(...) задаємо log_level.

Логування

Що логує log_level

Логує

Старт і зупинку HTTP-сервера, обраний transport (streamable-http), вхідні MCP-запити на endpoint /mcp (JSON-RPC: initialize, tools/call).

Не логує

API-запити qauto через httpx у tools. Якщо tool викликав get_cars, у stderr від log_level буде лише факт tools/call — без запиту на /api/cars.

Логування

Рівні log_level

Рівень — це фільтр «від і вище»: на INFO не видно DEBUG-рядків, на ERROR — ні INFO, ні WARNING.

  • DEBUG — максимум деталей: старт/стоп, bind host/port, transport, вхідні запити на /mcp
  • INFO — робочий режим: сервер стартував, слухає endpoint, прийшов MCP-запит
  • WARNING — лише попередження framework
  • ERROR — лише помилки на рівні сервера/transport
  • CRITICAL — критичні збої, сервер не може продовжувати роботу

Практика для qauto: локально — DEBUG/INFO; shared / production — WARNING/ERROR.

Логування

Налаштування log_level

Задаємо один раз у конструкторі — поруч із host/port:

mcp = FastMCP(
    name="qauto-course",
    host=MCP_HOST,
    port=MCP_PORT,
    streamable_http_path=MCP_HTTP_PATH,
    log_level=os.getenv("MCP_LOG_LEVEL", "INFO"),
)

Логування

logging (Python)

log_level покриває лише transport. Щоб бачити, що робить qauto server — виклики tools, запити до QAuto API, час відповіді — потрібен окремий шар: logging у Python + hooks httpx + wrapper для tools.

Два правила: донастройку логерів робимо після mcp = FastMCP(...), інакше він перезапише конфіг; stderr безпечний і для stdio, і для Streamable HTTP.

Логування

Чого не вистачає «з коробки»

  • httpx на INFO дає рядок без тіла request/response
  • httpcore на DEBUG засипає stderr трейсами — шум, а не користь
  • Вхідний tool видно як CallToolRequest — без імені, аргументів і часу виконання

Мета цієї частини — логувати вхідні tools і вихідні HTTP до QAuto з маскуванням секретів.

Логування

Env-налаштування

Поруч із MCP_* — змінні для application logging у config.py:

LOG_LEVEL = os.getenv("LOG_LEVEL", "INFO").upper()
LOG_HTTP_BODIES = os.getenv("LOG_HTTP_BODIES", "true").lower() not in ("0", "false", "no")
LOG_BODY_MAX_CHARS = int(os.getenv("LOG_BODY_MAX_CHARS", "2000"))

LOG_LEVEL — verbosity логера qauto_mcp; LOG_HTTP_BODIES — чи писати тіла запитів; LOG_BODY_MAX_CHARS — обрізка довгих JSON.

Логування

Маскування секретів

Ключі password, repeatPassword, sid, cookie, authorization замінюються на *** у logging_setup.py:

def redact_body(raw: bytes) -> str:
    """JSON → рекурсивно маскує ключі → обрізка до LOG_BODY_MAX_CHARS."""

def redact_mapping(data: dict) -> dict:
    """Для аргументів tool (наприклад credentials.password)."""

Логування

Вихідні HTTP: event hooks

У open_client() передаємо event_hooks в httpx.AsyncClient:

async def _log_request(request: httpx.Request) -> None:
    logger.info("→ %s %s", request.method, request.url)
    if LOG_HTTP_BODIES and request.content:
        logger.debug("→ body %s", redact_body(request.content))

async def _log_response(response: httpx.Response) -> None:
    await response.aread()
    logger.info("← %s %s (%.0f ms)", response.status_code,
                response.request.url,
                response.elapsed.total_seconds() * 1000)

У stderr з'являться → POST .../auth/signin, ← 200 ... ms, а на DEBUG — тіла з password/sid як ***.

Логування

Вхідні tools: LoggingFastMCP

FastMCP реєструє call_tool всередині __init__ — підміна після створення об'єкта не спрацює. Централізований варіант — підклас:

class LoggingFastMCP(FastMCP):
    async def call_tool(self, name: str, arguments: dict[str, Any]):
        started = perf_counter()
        logger.info("tool → %s %s", name, redact_mapping(arguments))
        try:
            result = await super().call_tool(name, arguments)
        except Exception:
            logger.exception("tool ✗ %s", name)
            raise
        logger.info("tool ← %s ok (%.0f ms)", name,
                    (perf_counter() - started) * 1000)
        return result

Усі tools (і майбутні) логуються в одному місці — схеми tools не чіпаємо.

Логування

Перевірка

  • 1. uv run python -m qauto_mcp — перезапустити сервер
  • 2. З Cursor викликати get_cars / add_car
  • 3. У stderr очікуємо ланцюжок: tool → add_car → → POST .../auth/signin → ← 200 ... ms → tool ← add_car ok
  • 4. password і sid у логах — лише ***
  • 5. LOG_LEVEL=DEBUG — з'являються тіла; LOG_HTTP_BODIES=false — лише method/URL/status/час

Фінал заняття

Підсумки

На цій лекції ми освіжили Streamable HTTP, перевели qauto MCP server зі stdio на мережевий transport і розібрали, як credentials переїжджають з env у headers клієнтського конфігу.

Також розвели два рівні логування: log_level FastMCP (transport) і logging додатку (tools + httpx до QAuto) з маскуванням секретів.

Ключова ідея: host, port і streamable_http_path — у конструкторі FastMCP; у run() лишається вибір transport. Далі — контейнеризація MCP server.
